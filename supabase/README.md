# Supabase backend

Postgres schema, RLS, RPCs, Realtime authorization, seed data and pgTAP tests for Gantry's
projects. Everything here runs locally with Docker and the Supabase CLI (3.0 or newer); the same
migrations are pushed to the hosted demo's project.

## Local workflow

| Task | Command |
|---|---|
| Start the stack (Postgres 17, Auth, PostgREST, Realtime, Storage, Studio) | `supabase start` |
| Show URLs and keys (local-only credentials) | `supabase status -o env` |
| Rebuild the database: migrations in order, then the seed files | `supabase db reset` |
| Run the pgTAP suite in `tests/` | `supabase test db` |
| Stop the stack (keeps the data volume) | `supabase stop` |

Run `supabase db reset` after every change under `migrations/`. Studio is at
http://127.0.0.1:54323, the API at http://127.0.0.1:54321, Postgres at
`postgresql://postgres:postgres@127.0.0.1:54322/postgres`.

### Seed order

`config.toml` lists the seed files in the order they run:

1. `seed.sql` (hand-written, idempotent): the two demo users in `auth.users`/`auth.identities`,
   their profiles, the project row (`snapshot = '{}'`) and the two memberships.
2. `seed_snapshot.sql` (generated by `scripts/gen-seed-snapshot.ts` from `packages/shared/src/seed`):
   upserts the Bryntum inline data, `handover_task_id` and the equipment booking.

Demo logins: `cm@demo.local` / `demo-cm-2026` and `pm@demo.local` / `demo-pm-2026`. Both see
costs and approve up to $250,000 (see [docs/SETUP.md](../docs/SETUP.md)).

## Access model

* Clients only ever read tables, and only rows of projects they are a member of
  (`public.is_project_member(project_id)`). `anon` has no table privileges at all.
* `project_members` is written by the service role only. `sessions` rows are inserted (`id`,
  `user_id`, `project_id`, `last_seen`) and heartbeated (`last_seen`) by their owner; `created_at`
  and the stored `last_seen` come from a trigger on the server clock, so the executor election
  (lowest `created_at`) cannot be rigged. Co-members can read sessions. A user can update their own
  profile (`display_name`, `color`).
* All writes to projects, revisions and commercial tables go through `security definer`
  RPCs (actor = `auth.uid()`) or the service role.

## RPCs (`public` schema, callable by `authenticated`)

| RPC | Behavior |
|---|---|
| `load_project(p_project uuid) -> jsonb` | `LoadProjectResult` from `packages/shared/src/revisions.ts`: `project { id, name, currency, handover_task_id (text or null) }`, `membership`, `snapshot`, `snapshot_revision`, `current_revision`, `revisions` (full rows with `revision_no > snapshot_revision`, ascending). |
| `submit_revision(p_project, p_client_id, p_local_revision_id, p_conflict_for, p_changes, p_origin default 'human') -> project_revisions` | Checks membership and that `p_client_id` is a `sessions` row of the caller in this project (refreshing its `last_seen`), then the store whitelist (`tasks`, `dependencies`, `assignments` and the record-less `project` key for everyone; `resources` only for role `cm`; `calendars` and unknown stores raise); locks the project row, returns the existing row for a repeated `(client_id, local_revision_id)`, maps every `added[*].$PhantomId` to a real id from `bryntum_record_id_seq` (reused across revisions via `record_ids`), deep-replaces phantom ids everywhere in the changes (fields, arrays, `$input`) except the `$PhantomId` key, sets `id` on added records, inserts with `revision_no = current_revision + 1`, bumps the head. `p_origin` is client-asserted metadata; `actor_user_id` (from the JWT) is the audit field. |
| `save_snapshot(p_project, p_revision, p_snapshot, p_session) -> boolean` | Stores Bryntum inline data for the head. `true` when `p_revision = current_revision`, `false` when stale (try again later). Raises when the caller is not a member or `p_session` is not their session. |

Errors use SQLSTATE `42501` for authorization failures and `22023` for invalid input, with a
message that names the store or parameter.

## Realtime

All topics are private channels (`supabase.channel(topic, { config: { private: true } })`),
authorized by policies on `realtime.messages`:

| Topic | Receive | Send | Source |
|---|---|---|---|
| `project:<id>:revisions` | members | nobody (clients) | trigger on `project_revisions` insert, event `revision`, payload = full row |
| `project:<id>:presence`, `:view`, `:cursor` | members | members | client broadcast / presence |
| `project:<id>:commercial` | members with `can_view_costs` | nobody (clients) | trigger on proposals, approvals, payment_authorizations, payment_events, agent_commands; event `change`, payload `{ table, id, op }` |

`can_join_project_topic(topic)` is the `select` (receive) policy, `can_send_on_project_topic(topic)`
the `insert` (send) policy: clients publish only on the ephemeral channels. A member who could send
on `:revisions` would make every other browser apply a payload that never passed `submit_revision`.
The triggers run as their owner (`postgres`, which bypasses RLS), so their rows are delivered.

`<id>` is the lowercase project uuid, exactly as Postgres returns it. The triggers call
`realtime.send(...)` only when it exists (`to_regprocedure` guard), so inserts keep working on
a database without the Realtime service; the local stack installs it, and `tests/06_realtime.sql`
asserts the broadcasts and the policies.

## The hosted demo's copies of Harbor

Each visitor gets a private copy of Harbor Street Offices for the visit (`20261110120200_copy_pool.sql`).
The seed writes twelve copies, `00000000-0000-4000-8000-000000010001` to `…010012`: unlisted, `template =
'harbor'` like Harbor itself, each with its own rentals, quote and `demo_seeds` row, and a free row in
`copy_pool`. Visitors sign in anonymously; clients never read `copy_pool` or `copy_seats`.

| RPC (`authenticated`, anonymous users included) | Behavior |
|---|---|
| `claim_copy(p_name default null) -> {project_id, join_token, join_code, lease_until, display_name}` | The caller's copy if they hold one; else a free copy (or one whose lease ran out, reset first), with the caller as its `cm` member in seat 1, held 30 minutes. A full pool raises SQLSTATE `53000` (HTTP 503 from PostgREST), "Every session is in use right now…". |
| `join_copy(p_token, p_name default null) -> {project_id, join_token, join_code, lease_until, display_name}` | While the lease holds: the next free seat (2 to 5), a `pm` member who sees costs; five people at most (`53300`, HTTP 503). A bad or expired token raises `22023` (HTTP 400). Someone already in it gets the same answer. |
| `join_copy_by_code(p_code, p_name default null)` | The same, with the copy's 6-digit `join_code` (spaces and dashes allowed). A code that matches no open session answers `{error: 'no_match', message, tries_left}` and is counted in `copy_code_misses`; after 8 in 10 minutes for the caller, or 20 in an hour from the caller's network, every code is refused with `PT429` (HTTP 429) for a while. |
| `copy_names_taken(p_token) -> text[]` (`anon` too) | The names in use in the session that invite token is for (none for any other token), so the welcome screen suggests a free one before sign-in. |
| `touch_copy(p_project) -> {lease_until, join_code}` | Any member: the lease runs 30 minutes from now, never past 2 hours after the claim. |
| `release_copy(p_project)` | The holder: `reset_demo_abandoning_payments`, the visit's files, payout approvals and quota counts removed, everyone who took a seat (and any anonymous member) removed, the copy freed. |
| `sweep_copies() -> int` (service role) | Frees every copy whose lease ran out; pg_cron runs it every 10 minutes (`sweep-copies`). |

Names come from a list of 30 in `copy_seat_names()` (`20261111010000_session_codes_and_names.sql`, the same list as
`apps/web/src/copy/names.ts`): the name asked for when it is on the list and free in that copy, else the person's
current name when it is, else a free one; nobody in a copy shares a name, and clients cannot change their profile's
name. A copy's `join_code` comes with its invite token and goes with it.

`app_flags` (`live_ai`, `live_calls`, `live_payments`) is readable by anyone and written by the service role.
`use_quota(p_kind, p_project, p_amount default 1) -> boolean` (service role) checks and counts a use against
`quota_limits` (`ai_turn` 40 per copy and 500 a day, `call_start` 30 a day with no limit per copy, `call_join` 40
and 300, `payout` 3 and 30, `payout_minor` $60,000 and $150,000, `invoice` 3 and 60; days in UTC; set in
`20261111040000_visitor_limits.sql`, `20261111130000_call_allowances.sql`, `20261111170000_calls_for_judging.sql` and
`20261111180000_calls_hardening.sql`); a copy's counts start over when it is reset.

A session's minutes with Remy on calls are a row of `remy_minutes` (the copy and its lease; 300 seconds, `quota_limits`
`remy_second`), which clients can't read. The site's call routes keep it with the service role: `remy_minutes_now`
reads it, counting a call that is over first; `remy_minutes_start` sets aside what is left for a call;
`remy_minutes_ended` counts a call when LiveKit reports that Remy left or that its room closed. `call_readiness` says
what a call needs as it stands (the switch, the starts, joins and turns left, and whether the day's spend has room), so
the page can grey its call button before anyone presses it.

## Hosted project settings

1. **Realtime → Settings → "Allow public access": off.** Only private channels are then served, so
   the `realtime.messages` policies are the sole gate on every project topic.
2. **Authentication → Providers → Email: on**, confirmations can stay on; the demo users are
   inserted already confirmed. Keep the JWT expiry short (Realtime caches channel authorization
   for the lifetime of the token).
3. Apply the schema with `supabase link --project-ref <ref>` then `supabase db push --remote`. (Since
   CLI v3 `db push` with no flag targets the local stack.) Seeds do
   not run on push: execute `seed.sql` and `seed_snapshot.sql` once against the hosted database
   (`supabase db query -f supabase/seed.sql --remote --yes`, then the snapshot file).
4. Turn on `pg_cron` (Database → Extensions): it runs the copies' sweep, which the migration
   schedules where the extension can be created.
5. **Authentication → Sign In / Providers → Anonymous sign-ins: on** for the hosted demo's visitors
   (`config.toml` turns it on locally). `seed_snapshot.sql` alone creates every project and the pool of
   copies; `seed.sql` adds the two demo logins, whose passwords are in this repository.
6. Never ship the `service_role` key to the browser; the web app uses the anon/publishable key and
   relies on RLS and the RPCs above.

## Troubleshooting

* **`Invalid login credentials` for the seeded users right after `supabase db reset`.** The auth
  container may still be restarting. Wait a minute and retry; if it persists,
  `supabase stop && supabase start`. The seed hashes
  use bcrypt cost 10 (`gen_salt('bf', 10)`), the same cost GoTrue uses for its own hashes.
* **`WarnSendingBroadcastMessage` in the Postgres log.** `realtime.send` swallows its own
  errors as warnings; the usual cause is that no `realtime.messages` partition exists for today,
  which the Realtime service creates once a WebSocket client has connected. The row insert that
  fired the trigger still succeeds.
* **`supabase test db` needs the full stack**, not just Postgres: `tests/06_realtime.sql` asserts
  that `realtime.send` exists and that broadcasts land in `realtime.messages`.
* The `postgres` role is not a superuser locally; migrations may create policies on
  `realtime.messages` but must not `alter table realtime.messages`.
